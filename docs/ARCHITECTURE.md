# Herix 架构原则

> 核心要求（2026-05-31 确认）：架构复用、灵活扩展、易维护

---

## 一、架构层面

**共享模块优先**
- 三端（赫使/商家/运营）共用的逻辑必须抽离到 `shared/` 目录
- 对 `shared/auth.js` 的调用必须通过 `Auth.xxx()` 接口，不绕过多重实现
- 新增共用功能优先考虑 `shared/` 目录，不直接内联到各端 HTML

**职责分层**
- `shared/`：纯业务逻辑，无视图依赖，只操作数据和回调
- 各端 HTML：负责视图层（HTML 生成、样式、交互绑定），调用 `shared/` 模块完成业务
- 后端 API：数据层，不做视图相关的逻辑

**统一入口**
- 同一个功能在三端不要出现三个独立实现
- 改动一处，其余自动生效（如登录流程，改 `auth.js` 三端同步）

---

## 二、代码层面

**可读性**
- 函数命名自解释，不依赖注释说明意图
- 配置项优于硬编码，options 对象可覆盖默认行为
- 单一职责：一个函数只做一件事

**可维护性**
- 共享模块提供明确的 `init()` 入口，业务方只需配置回调
- 模块内部使用 `window._authOnLogin` 等约定，支持动态替换而不污染全局命名空间
- XHR 请求错误处理集中管理，不在各端重复写 try-catch

**扩展性**
- 登录模块设计为可插拔：今天加 `autocomplete`，明天加 OAuth 或验证码，只需改 `auth.js`
- options 模式支持各端自定义：字段名、样式类、占位符、错误容器均可覆盖
- 后续新增 `shared/` 模块（如支付、通知、文件上传）沿用同一模式

---

## 三、约定

| 规则 | 说明 |
|------|------|
| `shared/*.js` 优先 | 共用逻辑先问"能否抽离成共享模块" |
| 配置优先于继承 | 使用 `extend(defaults, opts)` 模式 |
| 回调驱动 | 共享模块不直接操作 DOM，通过回调交给各端处理 |
| 单点修改 | 一个业务语义在一处修改，三端同步 |
